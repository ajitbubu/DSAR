# Unresolved Decisions (security and tenancy)

These haven't been assumed. Each shows the **MVP stand-in**, meaning what v1 does locally so work can proceed without committing to a production answer. "Blocks" says which milestone needs the decision before its exit.

| ID | Decision | Why it matters | MVP stand-in | Blocks |
|---|---|---|---|---|
| **D-1** | Production staff identity provider (Entra ID, Okta, Keycloak self-hosted, customer-supplied per tenant?), and whether roles come from IdP groups or the platform DB | Trust root for every staff action. Per-tenant IdPs change the tenant-resolution flow. | Keycloak in Compose. Roles stored in platform DB. | Prod only |
| **D-2** | Tenant isolation model: shared schema + RLS, schema-per-tenant, DB-per-tenant, or deployment-per-tenant. Is it the same for all tenants or tiered? | Blast radius of any authz bug. Contractual promises to customers. | Shared schema + app filter + RLS + composite FKs (ADR-0002). | Prod only |
| **D-3** | Key management: KMS/HSM vendor, key hierarchy (per-tenant KEK?), customer-managed keys (BYOK/HYOK), rotation period, who can decrypt | Protects all PII at rest, and evidence signing. | Local KeyProvider with a dev master key from env. Interface supports a per-tenant KEK. | Prod only |
| **D-4** | Evidence and audit retention: how long evidence packages and audit events are kept; whether WORM/Object Lock is required; legal basis | Conflicts with minimisation. Legal defensibility. Storage cost. | `retain_until` NULL. No Object Lock. No auto-deletion. | Prod only |
| **D-5** | Secret backend for connector credentials (Vault, cloud secret manager, customer-hosted) | Credentials reach customer production systems. | Env vars for mock connector tokens. | Real connectors |
| **D-6** | Data residency: must tenant data (DB, objects, logs, backups) stay in India or a customer-chosen region? Cross-border transfer rules. | DPDP s.16 transfer restrictions. Customer contracts. | Single local region. `tenant.data_region` column present but unused. | Prod only |
| **D-7** | Operator access model: break-glass procedure, just-in-time access, customer approval for support access | Insider threat (T-21). | No operator UI. Direct DB access in dev only. | Prod only |
| **D-8** | Evidence download mechanism: API streaming only, or short-lived presigned URLs (they carry a signature token in the URL) | Tokens in URLs vs API bandwidth. | API streaming (ADR-0007). | — |
| **D-9** | SLA values per right under DPDP (response days, clock start, pause rules) and who signs them off (legal) | Wrong values = regulatory breach. We won't guess legal timelines. | SLA policy rows with a placeholder value clearly flagged `UNVALIDATED` in the pack. Dashboard shows the flag. | M8 display |
| **D-10** | Upload policy: allowed file types, max size, whether malware scanning is required, and which scanner | Malicious uploads (T-18). | PDF/PNG/JPEG, 10 MB, magic-byte check. No AV. | M7 (limits), prod (AV) |
| **D-11** | Connector hosting for customer on-prem systems: SaaS-side connectors with inbound network access vs a customer-hosted agent that polls | Network trust boundary. Where credentials live. | Mock connectors in Compose. | Real connectors |
| **D-12** | Post-closure PII retention inside the platform: how long requester identifiers and discovery pointers are kept after closure, and in what form (hashed? deleted?) | The platform must not become a store of erased people's data (T-23). | Retained indefinitely in dev. Purge job designed but not scheduled. | Prod only |
| **D-13** | Staff MFA and session policy (MFA required? phishing-resistant? session lifetime, re-auth for approvals?) | Approval is destructive authority. Step-up auth may be needed. | IdP default. 8 h session. No step-up. | Prod only |
| **D-14** | Verification assurance levels per right/regulation (is OTP enough for erasure? what about correction or nomination? guardian/PwD flows) | Malicious-erasure risk (T-01). | OTP to the identifier being erased. Configured in the pack. | Prod only |
| **D-15** | Repository home: `DSAR/` currently sits inside the `~/Code-base` git repo. Init a standalone repo here, or move it? | Commits would otherwise land in the unrelated parent repo. | **Recommend `git init` in `DSAR/`** before scaffolding. | M0 |
| **D-16** | Minimum approver count and approver scope (one approver? two for bulk deletes? approvers per business unit?) | Strength of maker-checker. | One approver, ≠ maker, ≠ override author. | Prod only |
| **D-17** | Tenant resolution on the public intake form: custom domain per tenant, path slug, or embedded widget with a signed tenant token | Anyone can pick the tenant on the public form. That affects spam, abuse, and phishing look-alikes. | Path slug mapped server-side (`intakeSlug`). | Prod only |
